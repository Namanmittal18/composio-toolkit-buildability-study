# Can these 100 apps become agent tools?

An **evidence-backed agentic research pipeline** that assesses, for 100 applications,
whether each could realistically become an agent-callable **Composio toolkit** today —
capturing authentication, credential accessibility (self-serve vs gated), API surface
and breadth, MCP readiness, and a deterministic **buildability** verdict, with a
**source URL behind every important claim**.

It then **measures its own accuracy**, runs an **independent second-pass verification
loop**, corrects the errors it finds, and presents everything as a single, self-contained
HTML case study.

- **Case study:** `site/index.html` (open directly, or `npm run serve` → http://localhost:8080)
- **Final dataset:** `data/final/dataset.json` (also embedded in the HTML)
- **Verification:** `verification/{sample,accuracy,errors,analytics}.json`

---

## Assignment interpretation

The task is a small, real version of Composio's own pre-toolkit research. The valuable
output is **not** a 100-row table — it is a *trustworthy, scalable workflow*: convert a
repetitive research problem into an agent pipeline, ground every claim in primary
evidence, **measure the failure modes**, add independent verification, improve reliability,
and communicate the result clearly.

Key distinctions the pipeline enforces (from the brief):
API existence ≠ API accessibility · free product ≠ free API · OAuth ≠ self-serve OAuth ·
API ≠ MCP · official MCP ≠ community MCP · hosted API ≠ local CLI/library · a third-party
wrapper (e.g. `transcriptapi.com`) is the research target, **not** the underlying platform.

## Architecture

```
seed (apps.json)
   → source discovery      (pipeline/source_discovery)   queries + candidate doc URLs
   → retrieval             (web search + fetch)           primary docs: auth, pricing, API, MCP
   → extraction            (pipeline/extraction)          facts onto a strict schema (LLM stage)
   → evidence attachment                                   a source URL per important claim
   → schema validation     (pipeline/schema.py)           enums, evidence, impossible-combo checks
   → buildability scoring  (pipeline/scoring)             DETERMINISTIC rubric (single source of truth)
   → verification          (pipeline/verification)        independent 2nd pass + human sample + accuracy
   → correction                                            apply fixes, keep before/after
   → analytics             (pipeline/analysis)            distributions + cross-tabs
   → case study            (scripts/build_site.py)        self-contained HTML from the real JSON
```

A deliberate design choice: **buildability is never hand-authored.** The agent fills the
structured signals (auth / access / API / breadth / MCP / docs); `pipeline/scoring/buildability.py`
derives the score and label. Same signals → same verdict, every time.

### How the data in this repo was produced (honest note)

The Python pipeline is fully runnable with your own API keys. The dataset shipped in
`data/final/` was generated by the **Kiro research agent (Claude + built-in web search/fetch)**
executing this exact workflow, because no third-party API keys were configured in the build
environment. The **deterministic stages** (validation, scoring, accuracy, analytics, site build)
run in Python on that data and are reproducible by anyone — no keys required.

## Verification methodology

- **Sample:** 33-app stratified sample — easy, gated, trap (local CLI), low-confidence, and model-knowledge apps.
- **Independent second pass:** each sampled field is re-checked against primary sources — deliberately not the same reasoning that produced Pass 1.
- **Field-level accuracy** (not just row-level): auth, access, API type, breadth, MCP, buildability are each scored.
- **Before/after:** `data/raw/dataset_pass1.json` (Pass 1) vs `data/final/dataset.json` (corrected). Every correction is logged in `verification/errors.json`.
- **Result:** **Pass 1 = 96.0% → Pass 2 = 100.0%** on the sample (198 claims/pass). All 8 corrections were the same class: `mcp_status` under-reported for apps researched from model knowledge rather than live search.
- **How to read this number (honest framing):** Pass 1 = the original agent output scored against the independently verified answer; Pass 2 = the *corrected* dataset scored against that same verified answer. The +4.0 pts is therefore exactly the 8 real errors the second pass found and fixed (8 / 198 ≈ 4%), **not** an independent re-measurement claiming the full set is now flawless. Unsampled apps and undiscovered errors of the same class are not counted — see limitations below.

## Known failure modes / limitations

- **MCP "None found" is a lower bound** on apps not live-searched — the ecosystem ships new servers constantly; the 8 corrections prove this class is real.
- **Access is judged from documentation**, not by purchasing every product.
- **fanbasis** and **iPayX** are genuinely unverifiable → reported as `Unknown`, not guessed.
- **Verification covered 33 of 100 apps**; unsampled apps may carry the same error class.
- The app set skews API-first, so a high share is "Easy" — a property of the sample.

## Composio integration

Composio is wired as an **optional, key-gated, independent corroboration source**
(`pipeline/verification/corroborate.py`). With a `COMPOSIO_API_KEY` it looks the app up
in Composio's toolkit catalog (via the documented v3 Python SDK —
`Composio().toolkits.get(slug=...)` / `.list(...)`,
[SDK reference](https://docs.composio.dev/reference/sdk-reference/python/toolkits)) and
cross-checks whether a toolkit exists and which auth schemes it exposes against the
agent's auth/access findings.

**What is and isn't demonstrated (honest scope):**

- The assignment treats using Composio's SDK as *"in the spirit of the role"* — encouraged,
  not required. The hard requirement is an agent-driven pipeline, which is what ships here.
- This corroboration path was **not executed** for the shipped dataset: no `COMPOSIO_API_KEY`
  was configured, so `corroborate()` returns `None` for every app and **no result in
  `data/final/` depends on Composio**.
- The SDK calls target the documented v3 surface and read the response defensively, but the
  path is **best-effort and untested** without a key and a pinned SDK version. It is
  corroboration only — **never treated as ground truth**.

No key is committed or required, and the full pipeline reproduces without one.
